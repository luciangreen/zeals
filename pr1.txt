GitHub Agent Prolog Program Requirements

ZEALS: Zoned Expert Algorithmic Layer Synthesis

Target language: SWI-Prolog
Primary deliverable: PROGRAM_REQUIREMENTS.md
Implementation style: modular, deterministic where practical, test-driven, explainable, and suitable for staged implementation by a GitHub coding agent

⸻

1. Project Summary

Implement a SWI-Prolog system named ZEALS that generates a series of simplified algorithmic models, evaluates their strengths and failure boundaries, and synthesises their reliable components into a guarded expert algorithm.

A simplified model is called a perturbation.

Each perturbation solves a restricted version of a larger problem by changing one or more of the following:

* input domain;
* assumptions;
* representation;
* solving method;
* optimisation objective;
* resource limit;
* required output detail;
* level of approximation.

ZEALS must not treat any individual perturbation as an expert system. It must discover where each perturbation works, where it fails, and how its verified components can be combined with other perturbations.

The final expert algorithm must:

* classify an input problem;
* select an appropriate method;
* verify that the method is applicable;
* execute it;
* independently verify the result where possible;
* fall back to another method when necessary;
* explain its reasoning;
* return an explicit unresolved result when no safe method applies.

⸻

2. Primary Objectives

The implementation must support the following workflow:

Define problem
    ↓
Generate simplified perturbations
    ↓
Execute perturbations on test cases
    ↓
Measure behaviour
    ↓
Infer capability regions
    ↓
Detect failure boundaries
    ↓
Extract reusable components
    ↓
Construct a guarded expert algorithm
    ↓
Verify the synthesised algorithm
    ↓
Emit executable Prolog and reports

The system must prioritise:

1. correctness;
2. explicit assumptions;
3. explainability;
4. safe failure;
5. modularity;
6. reproducibility;
7. incremental extensibility.

Performance optimisation is secondary to semantic correctness in the first release.

⸻

3. Scope of the First Release

The first release must provide:

* a declarative problem-specification format;
* perturbation definitions;
* generation of perturbations from declared dimensions;
* execution of perturbations against cases;
* result and trace collection;
* capability-region inference;
* failure-boundary inference;
* component extraction;
* synthesis of guarded expert algorithms;
* independent result verification;
* explanation generation;
* Prolog source output;
* human-readable reports;
* unit and integration tests;
* a command-line interface;
* an interactive SWI-Prolog interface.

The first release does not need to:

* invent arbitrary Prolog code from unrestricted natural language;
* prove complete semantic equivalence between arbitrary programs;
* support distributed execution;
* modify its own source code while running;
* train statistical neural networks;
* depend on external machine-learning frameworks;
* provide a graphical user interface;
* guarantee optimal synthesis;
* solve unrestricted theorem-proving problems.

⸻

4. Terminology

4.1 Problem

A structured declaration of the task to be solved.

4.2 Case

A test or evaluation instance associated with a problem.

4.3 Perturbation

A restricted algorithmic model that solves a simplified version of a problem.

4.4 Capability region

The set of input features and conditions under which a perturbation is considered reliable.

4.5 Failure boundary

A minimal feature distinction separating known successful cases from known failing cases.

4.6 Component

A reusable part of a perturbation, such as a recogniser, solver, verifier, normaliser, estimator, or explanation generator.

4.7 Expert algorithm

A synthesised guarded algorithm that selects, applies, verifies, and explains methods across a wider domain than any single perturbation.

4.8 Synthesis plan

An intermediate representation describing how components are combined.

4.9 Verification

A check that a candidate output satisfies the original problem specification and declared invariants.

7. Core Data Model

7.1 Problem declaration

A problem must be representable as:

problem(
    ProblemId,
    Inputs,
    Outputs,
    Preconditions,
    Invariants,
    Objectives,
    Constraints
).

Example:

problem(
    solve_equation,
    [equation, target_variable],
    [solution_set, explanation],
    [well_formed_expression],
    [solutions_satisfy_original],
    [correctness, clarity, low_cost],
    [time_limit_seconds(5)]
).

The implementation may also support a dictionary form:

problem{
    id: solve_equation,
    inputs: [equation, target_variable],
    outputs: [solution_set, explanation],
    preconditions: [well_formed_expression],
    invariants: [solutions_satisfy_original],
    objectives: [correctness, clarity, low_cost],
    constraints: [time_limit_seconds(5)]
}.

The internal representation must be normalised before processing.

7.2 Case declaration

Cases must support:

case(
    CaseId,
    ProblemId,
    Input,
    ExpectedClass,
    ExpectedOutput,
    Metadata
).

ExpectedOutput may be one of:

exact(Value).
one_of(Values).
satisfies(Verifier).
unknown.
unsupported.

Metadata may include:

[
    tags([linear, exact]),
    source(user),
    difficulty(basic),
    expected_cost(low)
]

7.3 Perturbation declaration

A perturbation must include:

perturbation(
    PerturbationId,
    ProblemId,
    Restrictions,
    Assumptions,
    Representation,
    Method,
    Objectives,
    Contract
).

Example:

perturbation(
    linear_equation_solver,
    solve_equation,
    [degree_at_most(1), one_target_variable],
    [nonzero_denominators],
    expression_tree,
    isolate_variable,
    [exactness, clarity],
    contract(
        recognise_linear_equation,
        solve_linear_equation,
        verify_by_substitution
    )
).

7.4 Result declaration

Every execution must produce a structured result:

result(
    PerturbationId,
    CaseId,
    Status,
    Output,
    Cost,
    Confidence,
    Trace,
    Diagnostics
).

Supported statuses must include:

correct.
incorrect.
partial.
unsupported.
timeout.
exception.
contradiction.
unsafe.
unknown.
verification_failed.

7.5 Capability rule

capability(
    PerturbationId,
    PositiveConditions,
    NegativeConditions,
    Confidence,
    Evidence
).

7.6 Boundary declaration

failure_boundary(
    PerturbationId,
    BoundaryCondition,
    SuccessEvidence,
    FailureEvidence,
    Confidence
).

7.7 Component declaration

component(
    ComponentId,
    SourcePerturbation,
    ComponentType,
    PredicateIndicator,
    Contract,
    Metadata
).

Supported component types must include:

recogniser.
normaliser.
precondition_checker.
solver.
candidate_generator.
verifier.
error_detector.
cost_estimator.
confidence_estimator.
explanation_generator.
decomposer.
combiner.

7.8 Synthesis plan

The expert algorithm must first be represented as data.

Required synthesis terms:

guarded(Condition, ThenPlan, ElsePlan).
sequence(Plans).
fallback(Plans).
agreement(Plans).
union(Plans).
candidates(Plans).
refine(InitialPlan, RefinementPlan).
decompose(Splitter, Subplan, Combiner).
method(ComponentId).
verify(VerifierId, Plan).
explain(ExplanationId, Plan).
fail_with(Status, Reason).

10. Perturbation Generation

10.1 Generation dimensions

The generator must support these perturbation dimensions:

domain.
feature_set.
assumption_set.
method.
representation.
objective.
resource_limit.
output_detail.
approximation_level.
decomposition_strategy.

10.2 Perturbation specification

Generation rules should be declarative:

perturbation_dimension(
    ProblemId,
    Dimension,
    Values
).

Example:

perturbation_dimension(
    solve_equation,
    domain,
    [
        integers,
        rationals,
        reals
    ]
).
perturbation_dimension(
    solve_equation,
    method,
    [
        lookup,
        rearrangement,
        factorisation,
        quadratic_formula,
        numeric_search
    ]
).

10.3 Controlled combination

The generator must avoid unrestricted Cartesian explosion.

It must support:

generation_limit(MaxPerturbations).
compatible_setting(DimensionA, ValueA, DimensionB, ValueB).
incompatible_setting(DimensionA, ValueA, DimensionB, ValueB).
required_setting(DimensionA, ValueA, DimensionB, ValueB).

The generator must:

1. enumerate candidate combinations;
2. reject incompatible combinations early;
3. check required dependencies;
4. estimate the number of resulting perturbations;
5. warn or stop when a declared limit is exceeded.

Required predicates:

generate_perturbations(+ProblemId, -Perturbations).
generate_perturbations(+ProblemId, +Options, -Perturbations).
estimate_perturbation_count(+ProblemId, -Count).

Options should include:

[
    max_count(100),
    include_dimensions([domain, method]),
    exclude_settings([approximation_level(unbounded)]),
    deterministic_order(true)
]

11. Perturbation Contracts

Every executable perturbation must declare a contract:

method_contract(
    MethodId,
    Recogniser,
    Preconditions,
    Executor,
    Postconditions,
    FailureModes,
    Verifier
).

Before execution, the system must:

1. call the recogniser;
2. establish declared preconditions;
3. reject the method when its preconditions are not established;
4. execute the method in a protected context;
5. check local postconditions;
6. invoke its verifier;
7. record all stages in the trace.

A perturbation must never silently claim success when:

* a precondition is unknown;
* execution throws an exception;
* verification fails;
* output violates an invariant;
* a resource limit is exceeded.

15. Feature Extraction

Capability and boundary detection require explicit input features.

Each problem must declare or provide:

extract_features(
    +ProblemId,
    +Input,
    -Features
).

Features should be represented as ground terms:

[
    variable_count(1),
    maximum_degree(2),
    contains_division(false),
    contains_transcendental(false),
    coefficient_domain(integers)
]

Feature extraction must be deterministic for a given normalised input.

The system must support custom feature extractors per problem.

⸻

16. Capability-Region Inference

The first release must infer conservative symbolic capability rules from observed outcomes.

It does not need statistical machine learning.

The algorithm should:

1. collect features from successful cases;
2. collect features from failed and unsupported cases;
3. identify conditions shared by successful cases;
4. exclude conditions strongly associated with failures;
5. generate candidate positive and negative rules;
6. test the rules against all available evidence;
7. retain only rules meeting configured thresholds;
8. record evidence and confidence.

Required predicates:

infer_capability(
    +PerturbationId,
    +Results,
    -Capability
).
infer_capabilities(
    +ProblemId,
    +Results,
    -Capabilities
).
capability_applies(
    +Capability,
    +Features
).

The system must prefer rules that are:

* simple;
* conservative;
* explainable;
* supported by explicit evidence.

A rule must not be presented as certain unless all observed evidence supports it.

⸻

17. Failure-Boundary Detection

The boundary detector must compare successful and failing cases that differ minimally.

Required workflow:

Select success/failure pair
    ↓
Extract features
    ↓
Calculate feature difference
    ↓
Remove irrelevant differences
    ↓
Generate candidate boundary
    ↓
Test candidate boundary on other cases
    ↓
Store evidence and confidence

Required predicates:

detect_failure_boundaries(
    +PerturbationId,
    +Results,
    -Boundaries
).
minimal_feature_difference(
    +SuccessFeatures,
    +FailureFeatures,
    -Difference
).
validate_boundary(
    +Boundary,
    +Results,
    -Validation
).

The first release may use a greedy minimisation procedure.

It must document that inferred boundaries are evidence-based approximations unless formally proven.

18. Component Extraction

The system must extract reusable components from perturbation declarations and execution traces.

Required predicates:

extract_components(
    +PerturbationId,
    -Components
).
extract_all_components(
    +ProblemId,
    -Components
).
component_dependencies(
    +Components,
    -DependencyGraph
).

The system must identify:

* duplicate components;
* equivalent predicate indicators;
* declared dependencies;
* ordering requirements;
* incompatible components;
* components that require unavailable assumptions;
* components with insufficient verification evidence.

Component reuse must preserve the original contract.

A component must not be detached from a required precondition.

19. Dependency Graph

Components must be represented as a directed graph.

Example edges:

depends_on(linear_solver, expression_normaliser).
depends_on(substitution_verifier, expression_evaluator).
must_precede(expression_normaliser, linear_solver).
conflicts_with(exact_only_solver, approximate_only_output).

Required predicates:

build_dependency_graph(
    +Components,
    -Graph
).
topological_component_order(
    +Graph,
    -OrderedComponents
).
detect_component_cycles(
    +Graph,
    -Cycles
).

Cycles must be reported with actionable diagnostics.

The system must not emit an expert algorithm with unresolved dependency cycles.

20. Synthesis Strategy

The synthesiser must construct an expert algorithm from verified components and inferred capability regions.

Required phases:

1. collect candidate methods;
2. discard unsafe or unverified components;
3. group methods by capability region;
4. order specialised methods before general methods;
5. insert precondition guards;
6. insert verification steps;
7. insert fallbacks;
8. insert explicit unresolved branches;
9. produce an intermediate synthesis plan;
10. validate the plan;
11. emit executable Prolog.

Required predicates:

synthesise_expert(
    +ProblemId,
    -Plan
).
synthesise_expert(
    +ProblemId,
    +Options,
    -Plan
).
validate_synthesis_plan(
    +ProblemId,
    +Plan,
    -Validation
).

Options should include:

[
    prefer_exact(true),
    prefer_specialised(true),
    require_independent_verification(true),
    maximum_plan_depth(20),
    allow_approximation(true),
    unresolved_policy(return_unknown)
]

21. Method Ranking

Applicable methods must be ranked using deterministic scoring.

The score may consider:

* verified correctness;
* applicability confidence;
* exactness;
* coverage;
* expected runtime;
* expected memory;
* proof strength;
* explanation quality;
* failure risk;
* method specificity.

Required predicate:

rank_method(
    +ProblemId,
    +Features,
    +MethodId,
    -Score,
    -Reasons
).

Default ranking priority:

1. Satisfied safety requirements
2. Verified exact method
3. Strong applicability evidence
4. More specialised method
5. Lower expected failure risk
6. Lower expected execution cost
7. Better explanation support

A method that violates a required invariant must never receive a usable score.

⸻

22. Verification

Verification is mandatory for synthesised expert execution unless explicitly disabled for diagnostic purposes.

Required predicate:

verify_candidate(
    +ProblemId,
    +Input,
    +Candidate,
    -Verification
).

Verification results must include:

verified(Evidence).
failed(Reason, Evidence).
unknown(Reason).
unsupported(Reason).

Where possible, verification should use a method that is operationally independent from the candidate generator.

Examples:

* solve symbolically, verify by substitution;
* generate sorted output, verify order and permutation;
* classify input, verify required class invariants;
* derive a proof, verify each proof step.

The system must distinguish between:

* generation success;
* verification success.

A generated answer is not a valid expert answer until verification succeeds or the problem explicitly permits unverified output.

⸻

23. Expert Runtime

The emitted expert algorithm must follow this general behaviour:

expert_solve(Input, Result, Explanation) :-
    validate_input(Input),
    analyse_input(Input, Features),
    applicable_methods(Features, Methods),
    rank_methods(Features, Methods, Ranked),
    try_ranked_methods(Ranked, Input, Result, Trace),
    explain_result(Input, Result, Trace, Explanation).

The runtime must:

1. validate the input;
2. extract features;
3. identify applicable methods;
4. rank the methods;
5. try methods in ranked order;
6. verify each candidate;
7. stop after the first accepted verified result unless multiple solutions are required;
8. record failed attempts;
9. explain the selected method;
10. return unknown when no safe method succeeds.

Required unresolved form:

unknown(
    reason(NoApplicableVerifiedMethod),
    attempted(Methods),
    diagnostics(Diagnostics)
).

⸻

24. Conflict Resolution

When methods disagree, the system must apply these rules:

1. reject candidates that violate invariants;
2. reject candidates that fail verification;
3. prefer exact outputs over approximate outputs;
4. prefer candidates supported by independent agreement;
5. preserve multiple answers where the problem permits multiple valid solutions;
6. reject arbitrary tie-breaking between contradictory verified outputs;
7. return an explicit contradiction report when disagreement cannot be resolved.

Required predicate:

resolve_candidates(
    +ProblemId,
    +Input,
    +Candidates,
    -Resolution
).

Possible resolutions:

accepted(Candidate, Evidence).
accepted_multiple(Candidates, Evidence).
contradiction(Candidates, Diagnostics).
unknown(Reason).

31. Determinism Requirements

The implementation should be deterministic for:

* registration;
* validation;
* perturbation generation order;
* profiling;
* ranking;
* synthesis-plan generation;
* report generation;
* code emission.

Predicates intended to return one result should not leave unintended choicepoints.

Tests should use:

call_cleanup(Goal, Det = true)

or suitable SWI-Prolog determinism checks where practical.

Nondeterminism may be used internally for enumeration, but public deterministic predicates must collect or commit results explicitly.

Cuts may be used only when their operational meaning is local, documented, and covered by tests.

Prefer if-then-else, pattern separation, and once-like wrappers where clearer.

43. Final Design Principle

ZEALS must implement expertise as a transparent synthesis of bounded, testable algorithms.

The system must follow this principle:

Generate simpler models.
Test each model.
Identify where each model succeeds.
Identify where each model fails.
Extract only verified knowledge.
Guard every reusable method.
Combine compatible components.
Verify every candidate result.
Explain every accepted decision.
Return uncertainty when expertise is insufficient.

The generated expert algorithm must be broader than its perturbations without concealing their assumptions, limitations, or failure boundaries.
